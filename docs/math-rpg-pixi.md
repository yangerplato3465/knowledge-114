# 數學勇者 · PixiJS 導入評估

這份是**做 Pixi 之前的盤點與路線選擇**，不是實作規格。寫於 2026-08-26，當時一行 Pixi 都還沒寫。

- 素材處理流程（角色去背 vs 特效轉檔）→ 看 `.claude/math-rpg-fx.sh` 和 `.claude/math-rpg-keyer.ps1` 的檔頭註解，寫得很完整。
- 劍氣的軌跡、時序、爆擊怎麼運作 → 看 `assets/js/math-rpg.js` 的 `playSlash` 與 `SLASH_IMPACT_DELAY` 註解。
- **這份講的是「哪些東西值得搬進 Pixi、哪些不該搬、以及搬之前要先決定什麼」。**

## 0. 開始之前

**這台機器沒有 Node.js**，不能 `npm install pixi.js`。

> **2026-08-27 更新：本來這裡寫的是掛 CDN，已經改成本地檔。**
> ```html
> <script src="../assets/vendor/pixi.min.js"></script>
> ```
> 教室不一定有網路。頁面現在確實還吃 Google Fonts 和 FontAwesome 的 CDN，
> 但那兩個掛掉只是字醜、圖示變方框，遊戲照樣能玩；
> Pixi 掛掉是**整個戰鬥區空白**。這兩件事的嚴重性差太多，不能一起賭。
> 下載指令與說明見 `assets/vendor/README.md`。

功能不打折。實測 2026-08-26（`@8` 解析到 v8.20.0）：

| | 大小 |
|---|---|
| gzip 傳輸 | **231 KB** |
| 解壓後要解析的 JS | 818 KB |
| 目前整包遊戲圖檔 | 約 670 KB |

**載入量直接翻倍。** 走本地檔之後，「教室網路」那一項不再是風險，
剩下唯一真正的成本是**舊機器的 JS 解析時間** —— 818 KB 要 parse，低階機可能多花數百毫秒。

要瘦身得自己 build 只含需要的模組，但那需要 Node.js，這台機器沒有。

> 這一項要用 `pages/math-rpg-pixi-spike.html` 在**學校那台電腦**上實測，
> 不能在開發機上判斷。見第 5 節。

## 3. 架構上的關鍵決定

**如果只把 Pixi 當成疊在上面的特效層，粒子永遠只能在角色的「前面」或「後面」，不能穿插。**
劍氣從怪物身後穿到身前、碎片繞著角色飛，這類效果做不出來。

第 8 項（角色搬進 Pixi）是門檻 —— 過了這關 A 和 B 的所有項目才能互相疊加。
但它也意味著 `.sprite` 那整套 CSS 動畫要改寫成 Pixi ticker 動畫：
`lunge` `hurt` `die` `breathe` `floatIdle` `heavyIdle` `spawn` `shadowBreathe`

### 路線一：疊加層（保守）
只做 **1、2、6、10、18**。DOM 完全不動，隨時可以拿掉 Pixi。約能拿到七成的視覺提升。

### 路線二：戰鬥區全面 Pixi（徹底）
把 `#battle-stage` 整個換成一張 Pixi canvas，角色／劍氣／粒子／背景全在裡面。
血條、題目、按鈕留在 DOM。A + B 全部解鎖。

### 建議
~~**先做路線一的 1、2、10**，跑起來看實際感覺，再決定要不要投入路線二。~~

> **2026-08-27：這個建議被推翻了，改成先做角色 spike。理由與結果見第 5 節。**
> 簡短版：1、2、10 用 canvas 2D 就做得到（0 KB），做完驗證不到 Pixi 的價值；
> 真正只有 Pixi 能做的東西全部卡在第 8 項後面，所以先驗證第 8 項。

原本的理由（仍然成立，只是被「先驗證高風險項」蓋過）：
路線二會動到 `.sprite` 那整套已經調得很順的動畫，如果做完發現手感不如 CSS 版，回頭成本很高。

## 4. 導入時要小心的地方

- **劍氣的軌跡是 JS 現場量測的**（`playSlash` 量攻守雙方 sprite 中心）。若角色搬進 Pixi，這段要改成讀 Pixi 物件的座標，不能再用 `getBoundingClientRect`。
- **時序有三個數字綁在一起**：`slash.at = 0.26`、CSS `slashFly` 的 0.5s／53%、`SLASH_IMPACT_DELAY = 400`。改任何一個都要重算另外兩個。
- **特效素材已經把 alpha 烘進檔案**（`alpha = max(R,G,B)`），Pixi 裡要用加亮混合就設 `sprite.blendMode = 'add'`（v8 用字串，不是舊版的 `BLEND_MODES` 常數），不要重複做一次亮度轉透明。
- **`ParticleContainer` 有一個會影響效果規劃的硬限制：一個容器裡的所有粒子必須共用同一張底圖。**
  所以「火花 + 煙塵 + 碎片」不能塞進同一個容器 —— 要嘛開多個 `ParticleContainer`（各自一張圖），
  要嘛做成一張 texture atlas 再用 `uvs` 切。規劃第 2、5、10 項時要先決定走哪一種。
  另外它用 `addParticle()` 不是 `addChild()`，而且**一定要設 `boundsArea`**，
  否則容器的 bounds 回報為 0 會被 culling 當成不可見整個消失。
- 只有會逐幀變動的屬性要在 `dynamicProperties` 打開（預設只有 `position`）。
  粒子要變色或旋轉就得額外開 `color` / `rotation`，開越多每幀上傳 GPU 的資料越多。
- `unit()` 是量一個隱形探針元素拿到 `--u` 的實際 px 值。Pixi 場景的縮放要跟著這個走，否則在觸控電視上放到最大時粒子會小得像灰塵。

## 5. 角色 Spike 的結果（2026-08-27）

上面第 3 節建議「先做 1、2、10 再決定」。**那個順序後來被推翻了**，理由寫在這裡。

### 為什麼改成先做最高風險的那一步

1、2、10（拖尾、爆散、環境粒子）三項都是「畫幾百個加亮的小方塊」，
canvas 2D 配 `globalCompositeOperation = 'lighter'` 就做得到，**0 KB**。
做完只會知道「粒子好看」，不會知道 Pixi 值不值 818 KB。

真正只有 Pixi 能做的是著色器那批（#3 衝擊波位移、#4 爆擊色差、#5 剪影碎裂、
#8 受傷閃白／溶解、#19 灰階漸染），而它們**全部卡在 #8 這道門檻後面**。
所以先做 #8。

### 做了什麼

`pages/math-rpg-pixi-spike.html` —— 獨立的比較頁，**沒有動到遊戲本體**。
左右並排，同一組關鍵影格：左邊是從遊戲原封不動複製的 CSS `@keyframes`，
右邊是 Pixi ticker 逐格插值。按鈕同時觸發兩邊。

Pixi 這側刻意做成**兩層**對應 CSS 的巢狀結構：
外層 `Container` 跑 `lunge`/`hurt`/`die`/`spawn`，內層 `Sprite` 跑待機呼吸，
錨點都設 `anchor = (0.5, 1)` 對齊 CSS 的 `transform-origin: 50% 100%`。

### 量測結果

用 Web Animations API 把 CSS 動畫暫停在任意時間點、讀瀏覽器自己算出來的 `transform`，
跟 Pixi 在同一時間點的值逐點對照：

**四段動畫的所有停點與中間取樣點，位移誤差都是 0.00px。**

自己用 Newton 迭代解的 cubic-bezier，跟瀏覽器的實作在這個精度下沒有可測差異。

### 過程中抓到的坑（這是 spike 最有價值的產出）

> **CSS 的 `animation-timing-function` 是套在「每一段關鍵影格之間」，不是套在整段動畫上。**

第一版寫成後者，結果 `lunge` 在 38% 只衝到 x=38 而不是表定的 x=56，
衝刺的爆發力整個消失，看起來像軟綿綿地滑過去。
任何要把 CSS keyframes 移植到 ticker 動畫的地方都會踩到這個。

另外兩個小的：
- `ColorMatrixFilter` 的 `brightness()` / `saturate()` **每一個都是重設整個矩陣**，
  疊著呼叫會互相蓋掉。三個效果要一次算好成一個矩陣。
- `contrast(c)` 需要用到矩陣第 5 欄的**偏移量**（`0.5 * (1 - c)`），
  只改係數是做不出來的。

### 還沒驗證、也不該由程式碼回答的部分

- **肉眼手感沒有人看過。** 上面全部是數值比對，數值一樣不等於看起來一樣。
- **低階機器的 FPS 沒測過。** 要在學校那台電腦上開這一頁看右上角的數字。

### 下一步的判斷點

- 手感過關 ＋ 學校機器 FPS 可接受 → 走路線二（戰鬥區全面 Pixi），
  A、B 兩組項目全部解鎖，818 KB 花得值得。
- 手感不如 CSS 或機器跑不動 → **果斷放棄 Pixi**，改寫一層 canvas 2D 加亮粒子，
  拿路線一的七成效果、零依賴、零下載。

### 順帶做掉的事

`assets/vendor/pixi.min.js`（8.20.1，818 KB）已經抓成本地檔，**不走 CDN**。
理由見 `assets/vendor/README.md`：教室不一定有網路，
Google Fonts / FontAwesome 掛掉只是字醜，Pixi 掛掉是整個戰鬥區空白。

## 6. 第一步已上線：角色改由 Pixi 繪製（2026-08-27）

`assets/js/math-rpg-pixi.js`。**這一層只負責「畫」，不負責「動」。**

### 作法

DOM 結構完全保留，只是 `.sprite-body` 的 `background-image` 被設成 `none`
（`.sprite.pixi-drawn` 這個 class），角色改由一張 Pixi canvas 畫出來。
CSS 動畫照舊在跑，Pixi 每幀去讀 `.sprite` 與 `.sprite-body` 算好的
`transform` / `filter` / `opacity` 重畫一份。

**為什麼不讓 Pixi 自己跑動畫**（spike 已經證明做得到）：
math-rpg.js 有三個地方綁在 DOM 的角色元素上 ——
`playSlash` 量兩邊 sprite 中心算劍氣軌跡、`showDamage` 用 rect 定位傷害數字、
`fxSpawn` 把碎片插進 `#{side}-slot`。保留 DOM 當位置來源，這三個**一行都不用改**，
整步變成純加法、隨時可以撤。等這層穩定了再把動作搬進來，屆時只要換掉 `readPose()`。

### 量測

| | 結果 |
|---|---|
| 與 DOM 的位置吻合度 | `lunge`/`hurt`/`spawn`/`die` × 攻守兩側，最大誤差 **0.001px** |
| 每幀成本（含渲染） | **0.071ms**，約 60fps 預算的 0.4% |
| 受傷閃白 / 倒下灰階 | 由 `ColorMatrixFilter` 重現，逐點對得上 CSS |
| 退場 | 網址加 `?nopixi` 或 Pixi 載入失敗 → 自動回到純 DOM，實測無殘留 |

### 踩到的三個坑

1. **`setFromMatrix()` 會整個覆寫物件的 local transform。**
   貼圖的等比縮放跟 CSS 矩陣不能放在同一層，否則每幀被洗掉 ——
   症狀是角色尺寸變成 CSS 矩陣裡的縮放值（例如 spawn 起始的 0.9）。
   所以分兩層：holder 吃矩陣，內層 sprite 保留貼圖縮放。

2. **`offsetLeft` / `offsetWidth` 回傳整數。**
   `.sprite` 的 `left: calc(50% - 7*var(--u))` 是小數，四捨五入後產生固定
   x +0.5 / y −0.65px 的系統性偏移。改成在「`.sprite` 自己沒有 transform 時」
   用 `getBoundingClientRect` 量精確版面盒（idle 動畫掛在 `.sprite-body` 上，
   所以 `.sprite` 待機時確實是 `none`），量不到就先用整數版頂著、之後自動換掉。
   誤差從 0.7px 降到 0.001px。

3. **canvas 一定要插在第一個 `.fighter` 之前，不能 `appendChild`。**
   `.fighter` 有 `z-index:1` 且 `position:relative`，**會建立堆疊環境** ——
   碎片特效 `.fx`(z-index:3) 是關在 fighter 裡面的，整組仍以 z=1 參與外層排序。
   canvas 同為 z=1，同層時由 DOM 順序決定先後，`appendChild` 會讓角色蓋過
   碎片、名字、血條。正確的疊放是：背景 → 角色(canvas) → 碎片/名字/血條 → 閃屏 → 劍氣。

### 下一步可以做什麼

路已經開了 —— 角色在 canvas 裡，著色器可以上了：
- #2 命中爆散改 `ParticleContainer`，粒子能跟角色**同層互相穿插**（疊加層做不到的事）
- #6 受傷改成血花＋角色殘影
- #5 怪物死亡改成剪影碎裂
- #3 衝擊波位移著色器

真正把動作也搬進 Pixi（`readPose()` 換成 spike 的 `CLIPS`）要等
`playSlash` / `showDamage` 改成讀 Pixi 座標，那是另一步。

## 7. 特效 1～6 已上線（2026-08-27）

全部在 `assets/js/math-rpg-pixi.js`。**對 math-rpg.js 只動了 `strike()` 裡的一段**
（命中瞬間改呼叫 `MathRpgPixi.impactFx()`，Pixi 不在時退回原本的 DOM 碎片）。
受傷、死亡這兩個不用改任何東西 —— Pixi 自己看 `.sprite` 上的 class 變化。

### 場景變成三層

```
app.stage
 ├─ fxBack    粒子（角色之後）
 ├─ chars     player / enemy
 ├─ shatter   死亡碎片
 └─ fxFront   粒子（角色之前）
```

一次爆散有一半的粒子在角色**後面**。這正是第 8 項換來的東西 ——
只把 Pixi 當疊加層的話，粒子永遠只能整批在角色前面或後面。

### 六個特效

| # | 作法 |
|---|---|
| 1 劍氣拖尾 | 劍氣本身仍是 DOM，每幀讀它的 rect，沿路徑補間灑光點。因為粒子在 canvas 裡，拖尾會被角色遮住而不是浮在最上層 |
| 2 命中爆散 | 普攻 105 顆、爆擊 170 顆（舊版 11／20 顆 DOM span），前後層各半 |
| 3 衝擊波 | 自寫 GLSL 位移著色器，環狀往外擴 |
| 4 爆擊 | 徑向光束（拉長的光點）＋ RGB 色差著色器 ＋ 60ms 頓幀 |
| 5 死亡碎裂 | **不是粒子** —— 把角色貼圖切成 6×6，每片用自己的 UV 當獨立 Sprite 飛出去，碎片上看得到原本的紋理 |
| 6 受傷 | 紅色血花（方向朝被打飛的一側）＋ 4 張殘影（複製 holder 的矩陣，姿態一定跟本體一致） |

### 粒子系統的取捨

`ParticleContainer` 規定一個容器裡所有粒子共用同一張底圖。
與其做 atlas 切 `uvs`，這裡選擇**只用一張 64px 的柔邊光點**，
靠 tint／縮放／拉長變出火花、碎屑、血花、拖尾 —— 拉長的光點就是條狀火花，一張圖夠用。
底圖用 canvas 2D 畫徑向漸層產生：硬邊的圓點疊起來會有明顯邊界，柔邊才會在重疊處自然爆白。

粒子**預先配置 500/層、永不新增刪除**，死掉的 alpha 歸零收回池子。
ParticleContainer 增刪要重建 GPU buffer，每次命中噴 300 顆再刪掉會一直抖。

|---|---|---|

粒子／碎片／殘影／全螢幕濾鏡事後都歸零。

### 踩到的四個坑

1. **`Filter.from()` 在 8.20 不會自動補預設的 vertex shader。**
   只給 `gl.fragment` 會在 `ensurePrecision` 掛掉（`reading 'substring'` of undefined）。
   要明確給 `vertex: PIXI.defaultFilterVert`。

2. **`preference: 'webgl'` 一定要鎖。** 衝擊波與色差只寫了 GLSL 版本，
   autoDetect 在新版 Chrome 上可能挑 WebGPU，那兩個特效會整個失效。

3. **頓幀用 `ticker.speed = 0`，但不能「記下當下的 speed 再還原」。**
   兩次爆擊間隔小於 60ms 時，第二次記到的 speed 已經是 0，
   還原後 ticker 永久停在 0，所有特效直接死掉。固定還原成 1，
   被暫停的 CSS 動畫也要累積在一個 Set 裡一次全部放行。
   `updateFx` 另外加了一道保險：speed 是 0 但沒有頓幀在排程中就自己救回來。

4. **`watchClasses()` 必須排在角色迴圈之前。**
   它設 `n.shattered`，而角色迴圈要用那個旗標決定本體顯不顯示。
   放在後面的話碎裂／復原都會慢一幀。

### 已知限制

- **衝擊波推不動背景。** `.stage-bg` 還是 DOM 的 background-image，不在 canvas 裡。
  要做到「整個畫面被推開」，得先把場景背景也搬進 Pixi（第 9 項），那是另一步。
- 全螢幕濾鏡（衝擊波／色差）每幀多一次 render to texture，
  所以**沒有特效在跑時一定要把 `app.stage.filters` 設回 null**，不能常駐。

## 10. 勇者倒下：慢動作 ＋ 塵土（2026-08-27）

碎裂留給怪物。勇者是孩子的化身，碎成 36 片太狠，「消失」的意味也不對 ——
遊戲的用字本來就是「勇者倒下了…」，不是死亡。改成寫實路線：
倒地那一下時間拉慢，腳邊揚起塵土與小石子。灰階漸染（#19）保留，兩者疊在一起：
角色慢慢倒下，世界同時褪色。

### 時間預算（改數字前先看這個）

`damagePlayer` 排的是 `.die` 在 +320ms、`endGame` 在 +1150ms —— **中間只有 830ms**，
而 die 動畫本身就 850ms。拖慢之後若超過那個窗口，勇者還在半空中結算畫面就蓋上來了。

```
前 SLOWMO_MS 用 SLOWMO_RATE 倍速，之後恢復 1.0：
  300ms × 0.45 = 135ms 的動畫進度
  剩下 850 − 135 = 715ms 用正常速度跑完
  總計 300 + 715 = 1015ms   （比 1150ms 少 135ms）
```

第一版設 350ms，算出來 1043ms、只剩 107ms 餘裕，實測逼到 1.13s ——
離上限只剩 20ms，低階機器掉幾幀就會被切斷。縮到 300ms，視覺上分不出差別，餘裕多一倍。

### 幾個實作重點

- **CSS 與 Pixi 兩邊都要放慢**（`animation.playbackRate` ＋ `ticker.speed`）。
  只慢一邊會變成角色慢慢倒下、塵土卻用正常速度飛走，直接穿幫。
- **塵土必須用 `normal` 混合**，不能加亮 —— 加亮的土會發光，看起來像火花不像灰。
  `fxBack` / `fxFront` 那兩個容器是 `add`，所以另外開了一個 `dustPC`。
- **每 7 顆夾一顆小石子**（更小、更暗、彈更遠、落更快）。
  全是塵土的話畫面只有一團霧，沒有「撞到地面」的顆粒感。
- **觸地那一撮土用動畫進度判斷，不用 setTimeout。**
  中間有慢動作，寫死的計時器一定對不上觸地的那一格。
- 慢動作與頓幀都會動 `ticker.speed`，還原時要問對方還在不在跑（`restoreTickerSpeed`）。
- `clearGray()` 一併取消慢動作 —— 玩家可能在勇者還在倒地時就按「再挑戰」，
  不清的話新的一整場都是慢動作。

### 順手修掉一個既有的 bug：動作動畫從來沒在跑

做這一項時發現的，**不是這次改出來的**（`restart()` 與那四條 CSS 規則都不在我的 diff 裡）。

`.sprite.lunge` / `.hurt` / `.die` / `.spawn` 四條規則**特異性完全相同**（0,2,0），
同時命中時由「樣式表裡排最後的那一條」勝出 —— 而 `.spawn` 剛好排最後。
`restart(el, cls)` 只負責它被傳入的那一個 class，沒有人會把 `spawn` 拿掉，
所以 `beginBattle` / `spawnEnemy` 之後 `spawn` 就**永久黏在元素上**，
後續每一次 lunge / hurt / die 的 computed `animation-name` 都還是 `spawn`：

```
act(player,lunge) 後 animation-name = spawn   ← 修正前
act(player,lunge) 後 animation-name = lunge   ← 修正後
```

**角色的衝刺、受擊後仰、倒地整組動畫等於完全沒有在跑。**

之所以一直沒被發現，是因為打擊感的其他來源都還在：攻擊分鏡換圖、劍氣、畫面震動、
粒子，以及 `.sprite.hurt .sprite-body` 的閃白 ——
最後這條是**後代選擇器、作用在不同元素上**，不受這個覆蓋影響，所以閃白照常。

修法：`act()` 先把其他三個動作 class 移除再 `restart`（`ACTION_CLASSES`）。

> 也就是說 `pages/math-rpg-pixi-spike.html` 量到的 0.00px 一致性，
> 是因為那份測試自己有 `classList.remove('lunge','hurt','die','spawn')`，
> 繞過了這個 bug —— 量測本身沒錯，但它量的是「CSS 規則正常生效時」的情況。
> 現在遊戲裡也真的正常生效了。
