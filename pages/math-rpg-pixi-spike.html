這個 spike 在驗證什麼

  • 手感能不能 1:1 重現。 左右的數值表是同一份，差異只會來自插值與 easing 的實作。
  • 巢狀 transform 有沒有正確對應。 CSS 是兩層：.sprite 跑動作、.sprite-body 跑待機呼吸。 Pixi 這邊也做成兩層（外層 Container ＝ 動作，內層 Sprite ＝ 待機），錨點都設在 50% 100%（anchor = (0.5, 1)） 對齊 CSS 的 transform-origin，縮放與旋轉才會繞同一個點。
  • 受傷閃白：CSS 用 filter: brightness(2.8) saturate(0.1)，Pixi 用 ColorMatrixFilter。 這是 Pixi 真正的價值所在 —— 同一條路上還有溶解、色差、殘影，CSS filter 做不到。
  • 效能：右上角的 FPS 是 app.ticker.FPS。學校的低階機器要看這個數字。

量測結果（2026-08-27）

用 Web Animations API 把 CSS 動畫暫停在任意時間點、讀瀏覽器自己算出來的 transform， 跟 Pixi 在同一時間點的值逐點對照：

  • lunge / hurt / spawn / die 四段， 所有關鍵影格停點與中間取樣點的位移誤差都是 0.00px。 自己解的 cubic-bezier（Newton 迭代）跟瀏覽器的實作在這個精度下沒有可測差異。
  • 過程中抓到一個真 bug，也是這個 spike 唯一真正的產出： CSS 的 animation-timing-function 是套在「每一段關鍵影格之間」，不是整段動畫上。 寫成後者的話，lunge 在 38% 只會衝到 x=38 而不是 x=56，衝刺的爆發力整個不見。 見 sampleClip() 的註解。

還沒驗證的部分

  • 肉眼手感沒有人看過。 上面全部是數值比對。 數值一樣不等於看起來一樣（動態模糊、合成時機、螢幕更新率都可能造成差異）—— 請自己開這一頁按幾下，這是這個 spike 唯一要你做的事。
  • 低階機器的 FPS 沒測過。 右上角的數字要在學校那台電腦上看才算數。
  • 倒下的 filter: grayscale(0.75) brightness(0.85) 在 Pixi 是手寫色彩矩陣。 數值有對齊 CSS 的 luma 係數，但沒有逐像素比對過，顏色可能有肉眼可見的小差。
  • 劍氣只有 Pixi 那側有。素材的 alpha 已經烘進檔案（見 .claude/math-rpg-fx.sh）， Pixi 這裡設 blendMode = 'add'，不要再做一次亮度轉透明。
